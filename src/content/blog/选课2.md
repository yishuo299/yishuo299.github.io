这一篇换一种写法，直接从业务规则切进去。选课系统最核心的地方不是“点击按钮”，而是点击之后系统到底检查了什么。

学生选课至少要回答几个问题：

- 这门课还开放吗？
- 学生是不是已经选过？
- 人数是不是满了？
- 上课时间会不会冲突？
- 学生科别和课程科别是否匹配？

## 选课入口

后端核心逻辑在 `CourseSelectionServiceImpl`。学生提交选课后，系统先查询开课信息：

```java
CourseOffering offering = courseOfferingMapper.selectOfferingDetail(offeringId);
if (offering == null) {
    throw new BusinessException(ResultCode.DATA_NOT_FOUND, "课程不存在");
}
```

这一步防止前端传入不存在的课程 ID。后端不能相信前端页面，因为用户可以直接请求接口，所以所有关键校验都必须放在后端。

## 检查课程是否开放

```java
if (offering.getStatus() != 1) {
    throw new BusinessException(ResultCode.COURSE_SELECTION_NOT_OPEN, "该课程选课未开放");
}
```

开课状态决定学生能不能选择。项目里开课状态由教务管理员维护，可以开放、关闭或结束。

## 文理科匹配

项目中课程和学生都有 `streamType` 字段。学生只能选择和自己科别一致的课程。

```java
Integer studentStream = sysUserMapper.selectStudentStreamType(studentId);
int studentStreamType = (studentStream != null ? studentStream : 1);
int offeringStreamType = (offering.getStreamType() != null ? offering.getStreamType() : 1);

if (studentStreamType != offeringStreamType) {
    String streamName = offeringStreamType == 1 ? "文科" : "理科";
    throw new BusinessException("此课程为" + streamName + "课程，您无法选择");
}
```

这个规则让课程不只是“能不能选”，还要“适不适合当前学生”。前端也做了置灰提示，但真正的限制还是后端完成。

## 重复选课和容量校验

```java
if (selectionMapper.checkSelected(studentId, offeringId) > 0) {
    throw new BusinessException(ResultCode.COURSE_ALREADY_SELECTED, "您已选择该课程");
}

if (offering.getSelectedCount() >= offering.getMaxStudents()) {
    throw new BusinessException(ResultCode.COURSE_FULL, "课程人数已满");
}
```

这两段分别处理重复选择和课程满员。课程容量是选课系统里非常重要的限制，否则同一门课可能被无限选择。

实际写入前，系统还会调用 `incrementSelectedCount` 增加已选人数：

```java
int rows = courseOfferingMapper.incrementSelectedCount(offeringId);
if (rows == 0) {
    throw new BusinessException(ResultCode.COURSE_FULL, "课程人数已满");
}
```

这里再次判断 `rows == 0`，是为了避免并发情况下人数已经被其他请求抢满。

## 时间冲突判断

```java
public boolean hasTimeConflict(Long studentId, Long offeringId) {
    CourseOffering offering = courseOfferingMapper.selectById(offeringId);
    if (offering == null || offering.getDayOfWeek() == null) {
        return false;
    }

    List<CourseOffering> conflicts = courseOfferingMapper.checkTimeConflict(
        studentId,
        offering.getSemesterId(),
        offering.getDayOfWeek(),
        offering.getStartSection(),
        offering.getEndSection()
    );

    return !conflicts.isEmpty();
}
```

这段逻辑的关键是比较同一学期、同一天、节次区间是否重叠。只要已经选过的课程和新课程时间冲突，就不能继续选择。

## 退课逻辑

退课不是直接删除记录，而是把选课状态改为无效，并减少已选人数。

```java
selectionMapper.update(null,
    new LambdaUpdateWrapper<StuCourseSelection>()
        .eq(StuCourseSelection::getId, selection.getId())
        .set(StuCourseSelection::getStatus, 0)
);

courseOfferingMapper.decrementSelectedCount(offeringId);
```

这种做法保留了历史记录，也让学生后面重新选课时可以复用旧记录。

## 课表生成

课表页面不是手写死数据，而是根据学生已选课程生成 `ScheduleVO`。

```java
List<CourseOffering> offerings = courseOfferingMapper.selectStudentSelectedCourses(studentId, semesterId);

for (CourseOffering offering : offerings) {
    ScheduleVO schedule = new ScheduleVO();
    schedule.setCourseName(offering.getCourseName());
    schedule.setTeacherName(offering.getTeacherName());
    schedule.setClassroomName(offering.getClassroomName());
    schedule.setDayOfWeek(offering.getDayOfWeek());
    schedule.setStartSection(offering.getStartSection());
    schedule.setEndSection(offering.getEndSection());
    scheduleList.add(schedule);
}
```

前端再把这些数据渲染成星期和节次组成的课表。

## 小结

这部分真正完成的是一条完整的学生选课链路：查询课程、执行校验、写入选课、更新人数、退课恢复、生成课表。它看起来是一个按钮，背后其实是一组业务规则在保护数据不乱。
