# 文章与源码整理

## 文章要能支持工程复现

默认采用架构/复现优先的工程文章，帮助有基础的读者结合源码运行并了解项目。内容要求如下：

1. 项目介绍：服务对象、问题、业务边界，区分完成的功能与扩展建议。
2. 功能介绍：按角色和完整流程描述用户可见结果，而不是仅罗列技术名。
3. 工程构成：目录树、入口、核心文件、数据表/模块关系、前后端数据流。
4. 设计思路：为何采用当前模型、状态机、权限划分、协议或算法，解释输入、输出和约束。
5. 技术栈：从配置确认版本或版本范围，说明每种技术在工程中的职责。文章完整栈与博客六类筛选标签分开。
6. 复现：环境、依赖、建库、配置变量、启动/构建、访问地址、公开演示账号与逐步验证点。命令按工程当前目录写，避免作者机器绝对路径。
7. 关键实现：中大型项目至少十段，随项目规模增加；覆盖权限、查询、校验、状态流转、业务核心、金额/库存/算法、错误与数据一致性，而不是把十条配置当关键代码。
8. 运行结果：界面、测试场景、可观察状态变化和预期输出；与原代码及实际测试相符。
9. 总结：展示项目能力与有依据的扩展方向；“技术支持与致谢”按使用到的开源技术编写。

每段代码附标题、使用方法、项目作用和源码相对位置。摘录源码中的真实代码；省略无关代码时标明省略。改写后的流程只可标为伪代码或说明，不冒充原实现，不虚构类、函数或服务。不能把构建成功当成业务完成的证据。

面向公开读者，语句连贯、布局清晰、长代码可横向滚动，手机阅读不溢出，字体与卡片背景对比充足。不得出现“给 AI 使用”“视频脚本基础”“内部发布说明”等制作备注。不同候选文章必须在顺序、讲解路线、版式和风格上不同，而非仅替换措辞。

图片放在所证明的功能或实现附近，配短图注。UI 截图靠近对应功能，架构/电路图靠近构成，结果图靠近验收。没有图片时不虚构图片链接，不把所有图片堆到文末。链接包含下划线时保持真实 URL；README 图片用 GitHub 可解析相对路径或有效图床链接。

当前动态文章数据结构见 `src/data/multiProjectArticles.ts` 与 `src/pages/projects/[slug].astro`。若 schema 没有摘要、图注、技术职责等必要字段，可按需要扩展兼容字段，或采用已有单独 Astro 文章模板；不要因模板只支持短字符串而削减文章要求。

## 卡片与文章关联

卡片只包含项目名称、简洁功能概况、技术分类与短介绍；具体实现写在全文。卡片必须关联 articleUrl，真实公开仓库关联 projectUrl。在文章标题旁、结尾以及介绍面板“阅读完整文章”左边提供“前往项目”；沿用现有导航行为，避免点击外部链接冒泡触发文章导航。

用户交来的成稿 MD 可以作为起点，但仍需用源码核实功能、关键代码和运行步骤。不要未经核实照抄附带文档中的私人配置或旧路径。

## 按请求整理 GitHub 工程

只在任务包含整理/脱敏/复制工程时执行，不因仅写文章而改源码。确认指定目标与项目及 Git 远程一致；保留目标 `.git`，原工程保持可恢复。按当前项目更新目标，不复制依赖目录、编译缓存、日志、IDE 私人配置、真实上传数据或开发者环境文件。

扫描实际内容：数据库密码、JWT/Django secret、API token、签名证书、个人证件/手机号/地址、私人图片、数据库生产数据、本机用户名及绝对路径。不要把扫描到的秘密原文输出到对话。示例账号与虚构数据可保留，并明确其演示性质；不把真实个人数据换个姓名就称为已脱敏。

将实际秘密替换为环境变量读取，在 `.env.example` 提供占位符，`.gitignore` 排除真实 env、缓存、依赖与运行上传文件。说明框架是否自动读取 `.env`；不自动读取的 Spring/Django 工程需要写出系统环境变量设置或显式加载方法。

替换真实生产数据为足量合成数据，关联主外键和状态保持一致。配置外置后重新验证构建和启动设置；默认本地开发值不得被写成安全生产设置。不要盲删运行所需的预构建前端、静态图片、SQL 或合法演示资源。

中文 README 包括介绍、功能、技术栈及职责、角色、结构、数据库初始化、配置表、启动/构建、访问地址、演示账号、复现结果、常见问题、技术支持与致谢。数据库初始化脚本若会 DROP 数据库，明确说明会重置数据。公开文档不添加“公开发布/脱敏完成/个人信息删除”内部检查章节。

提交前检查 Git 实际追踪内容，说明脱敏的是当前工程；仅修改文件不代表历史提交中的秘密已移除。不要未经请求改写 Git 历史或推送。
