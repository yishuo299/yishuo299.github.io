# 体验实现与验收

## 忠实复刻原项目

体验是完整计算机项目的独立前端版本，外观、页面顺序、布局、配色、文字、菜单、表格、表单、弹窗、图表和交互尽量与原界面一比一对应。优先复制/构建原 frontend 并替换数据适配层；服务端模板项目可将原模板和资源转为静态前端。禁止用统一后台模板或只借用原项目风格代替页面。

原工程继续可运行。博客体验位于 `public/experience-native/<slug>/`，入口 `/experience/<slug>/` 套用现有测试人员工具栏。独立资源本地化，避免字体、图库、CDN 或后端失联拖慢首次进入。未获授权不安装后台服务来替代纯前端体验。

## 先制定业务清单

逐个角色对照原页面、API 模块、Controller/View/Service 和数据库：

| 角色/页面 | 原功能和规则 | 模拟逻辑入口 | 初始测试数据 | 操作与预期结果 | 实测状态 |
| --- | --- | --- | --- | --- | --- |
| 按项目填写 | 包括权限/校验/状态变化 | 指向真实处理函数 | 覆盖正常及边界状态 | 列出可观察结果 | 通过/失败/未执行 |

所有增删查改、分页、组合筛选、详情、业务动作、上传/导出、统计和错误反馈均纳入清单。项目中的硬件、摄像头或外部支付若不能真实执行，提供明确模拟交互和结果，不能假称已对真实设备/真实交易验证。

## 模拟后端必须遵守原协议

- 读取实际 Axios/fetch 封装：baseURL、method、请求体、参数、Authorization、响应业务 code 和 data 包装层。
- 逐接口返回原页面真正消费的字段名、类型、数组/对象层级。Axios 拦截器可能返回整个 wrapper，也可能直接解包 data；不能混淆。
- 建立内存 store 和派生函数，CRUD、列表、详情、图表、统计读取同一份数据。
- 把后端校验、权限、主外键限制、金额算法、状态机、库存/余额变更和审计流水迁移到 JS。后端事务在前端表现为先检查全部条件再原子更新内存，失败不能留下半完成状态。
- 非法动作返回有意义的业务失败：重复预订、库存不足、已缴账单再次支付、终态工单继续处理、删除被引用记录、越权访问等规则以原工程为准。
- 不用通用 `ok(null)`、固定 `true` 或伪造统计冒充尚未实现接口。识别未知接口，补齐处理，并在验证阶段让遗漏可见。
- 真实 API 请求不得流到外部或已关闭后端。需要支持 fetch 与 XHR 的项目覆盖两者；拦截范围限定于项目 API，不拦截静态资产。
- 上传在当前会话生成可显示 object URL/本地演示资源并正确清理；导出生成可下载的有效 CSV/XLSX/原格式文件，而不是把 JSON 命名成 xlsx。

可沿用共享 `mock-api.js` 的对应项目分支，或新增项目内适配器。不要让共享与项目脚本同时重复拦截同一请求；注册位置明确，加载顺序在入口应用模块之前。

## 数据与角色

初始合成数据不能只给一个空表：覆盖主要角色、多个实体、分页、未处理/处理/完成等状态、足量金额和历史记录。初始日期依赖今天的流程可用相对日期生成；不要因演示数据过期而无法提交或筛选。所有计数和金额应动态派生，例如：

- 停车：总车位 = 空闲 + 占用 + 预约 + 维护，在场车辆与入场记录及占用车位一致；出场联动费用、流水和车位。
- 酒店：预订区间冲突、库存、入住、换房、消费、房费、押金、退款和清洁联动。
- 物业：报修派单/处理/评价状态合法；分次缴费联动欠款、账单状态、流水、统计。
- 财务：账户余额、收支流水、预算、转账两端及看板一致。
- 其他项目按其实际业务建立对应约束，不能因为有表格就认为已覆盖。

每个原角色至少一个测试身份，与 roleConfigs 的 key、角色枚举、用户 ID、关联档案 ID 和起始路径严格对应。管理员和普通用户实际返回的数据范围不同。

业务数据不写入 localStorage、IndexedDB 或服务端，刷新应重建初始数据。登录身份可使用现有角色引导方式；如果角色切换会重新加载 iframe 并重置数据，应沿用/说明当前行为。不要给刷新加持久化。

## 首次加载与资源

- 体验外壳 iframe 初始 `about:blank`；准备身份再设置 src。同一 DOM 只初始化一次，重复点击当前角色不重复加载。
- 检查 `localStorage`/`sessionStorage` 的原键及角色字段，iframe 与父页同源时使用一致的存储策略；不要靠刷新碰巧读到旧身份。
- Vite 的入口 JS、CSS、dynamic import、modulepreload 映射、public 图片和字体全部检查；`index.html` 改路径不代表懒加载模块也已修复。
- 原 `/static/`、`/assets/`、`localhost` 地址需适配到实际体验子目录，修复时优先重新构建正确 base。批量改构建文件时限定准确前缀，避免改坏业务字符串。
- Hash Router 适配 `#/<route>`；History Router 需要正确 base 与 GitHub Pages 刷新策略，不能把父博客 URL 改为体验工程的根路由。
- 监听返回、重新进入和首次懒加载错误；加载状态应有结束与失败恢复，不留下遮罩/滚动锁。

## 验证顺序

1. 静态检查：项目数据、唯一 slug、六类筛选、路由生成、静态资产与懒加载路径、正确模块顺序。
2. 业务验证：依功能表测试各角色的 CRUD、组合查询、核心状态流转、异常校验、联动统计、下载/上传以及刷新重置。Node 模拟验证可测试处理函数，但不能代替浏览器前端运行。
3. 浏览器行为：首次直接打开、首页点击进入、站内导航、每个角色切换、返回后重新进入；检查页面可见内容、未捕获异常与失败请求。未获用户视觉验收授权时可做程序运行检测，不自行展开主观视觉验收；尊重用户自行验收外观的偏好。
4. 性能：文章/体验背景无持续循环，角色初始化只发生一次，不加载其他项目完整 bundle，隐藏页/离开页释放动画。手机入口、表格滚动、响应式卡片和导航可用。
5. 集成：执行博客 `npm run build` 和 `git diff --check`，源码整理任务再跑相关后端/前端检查；没有数据库时不能声称后端业务实测完成。

报告通过与缺项，记录可复现测试步骤。不承诺所有设备绝对零卡顿；以实际执行的构建、浏览器和业务验证为证据。
